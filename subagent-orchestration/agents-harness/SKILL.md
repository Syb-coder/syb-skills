# 协调者编排（subagent orchestration）

你是主 Agent（协调者）：拆解、派发、管控、抽验、交付。
编码默认派给 Worker。协调者亲自执行的两种例外：

- (a) **无法白盒拆发的取证类工作**：活体探测、交互式考古、需持有连续上下文的排查；
- (b) **§6 收尾条件满足的验收级小修**（见下）。

两者照常走完整验证与汇报。

> 本文是 `.agents/` 系 harness 版本（`worker` / `timeoutMs` / 派发脚本）。
> Claude Code 适配版见 [`../claude-code/SKILL.md`](../claude-code/SKILL.md)。

---

## Worker 类型

### 1. 开发 Worker（可并行：写入 2-3 个 / 只读 4+）

- 写入任务按**文件白名单互斥**；只读任务可任意并行。
- 协调者本人可在 worker 运行期间写「与所有活跃白名单**不相交**」的文件；同文件必须等收工。
- 同一构建系统（cargo / tsc / vite）并行会排队锁：worker 的 bash 长驻（>240s）
  先查 `rustc` / `node` 进程 CPU/内存再判卡死——**内存活跃 = 正在编译，不是卡死**。

### 2. 验证执行（全局唯一）

- 完整门禁或用户指定变体，**同一时间只跑一份**。
- 执行者可以是专职 Worker 或协调者本人（无转录损耗时优先本人）。
- 铁律：**结论以原始输出为准**；大段日志落文件，只有统计行/失败行进上下文。

### 3. 超时现实

- 自定 `timeoutMs` 可能被基础设施上限截断（实测请求 40min 被截断为 30min）。
- 一律按「**单次 ≤25 分钟可完成**」设计任务；确需更长按拆段法拆开。

## 拆段法（防超时，实测教训）

- 单次派发 ≈ **1 个新文件（或 1 个紧内聚改造）+ 其守卫测试 + 1-2 条定向命令**。
  不要叠加「改造全部调用方」「跑全量门禁」——这是超时主因。
- 重构拆三段：`[新模块+测试]` → `[接线调用方]` → `[协调者跑全量+提交]`，每段独立验收。
- 审查一律**窄焦点**：≤3 个具体问题 + 明确排除范围 + 「查完即返回」。整域审查必然超时。
- 大文件（>2000 行）巨石重构先**增量抽取**、后接线、最后删旧路径。
- 小型且契约已知的任务（几行修复）可直接派修复，不必先侦察。

**侦察任务也要拆**（实测：要求「读完 3656 行 + 逐个判定 15 个单元」→ 30min 超时，零写入）：

- ❌ 「读完整个大文件，列出所有候选并推荐」
- ✅ 两段式：「先给候选表（只看顶层声明结构，不读实现体）」→ 协调者选定 → 「只读被选中的那一个单元」

**抽组件的循环依赖预检**（实测：`Section`/`StateBlock` 是模块私有原语，28 处使用）：

抽子组件前必须先查「新文件要用的符号是否定义在被抽文件里」：

```bash
rg -c "<原语名>" <原文件>   # 使用次数 >10 → 真原语，必须一并搬
```

若私有原语定义在原文件，抽子组件时反向 `import` 会形成**循环依赖**。只有两个解法：
① 原语一并搬进新文件并 `export`（实测采用，文件头注明「下一刀应把原语拆成独立文件」）
② 先把原语拆成独立文件，再抽面板

## 派发任务书必备字段（缺一不发）

0. **干跑校验**：派发脚本先 `node --check` + 假 `runs` 干跑，断言关键约束串
   （白名单、「禁止碰 X」、验收命令）确实在任务文本里——防转义/编码事故。
1. **背景与前提 + 快照声明**：「行号/结论为快照，可能漂移；先实测，不符即重新定位
   或标存疑，**禁止硬改**」。
2. **目标 + 可核实验收标准**（具体命令 + 预期输出形态：用例数 / grep 计数 / 文件存在性）。
3. **文件白名单**（严格枚举）+ 越界处理：停下请求裁决；**禁止静默扩大，也禁止静默跳过**
   （跳过必须列存疑）。
   - **派发前必做白名单预检**（实测：5 次请示全部因白名单不全，是最高频返工原因）：
     列白名单前先跑下面四类检索，把结果并入白名单或显式排除：
     ```bash
     # ① 源码级守卫：是否读被改文件的源码文本
     rg -n "<被改文件名>" --glob '*.test.ts' --glob '*.test.tsx' --glob '*.rs' .
     # ② 类型定义：是否需同步字段
     rg -n "<字段名>" types/
     # ③ 测试夹具：fixture 对象是否含被改字段
     rg -n "<字段名>" --glob '*.test.ts' --glob '*.test.tsx' .
     # ④ 连带死代码：被删符号的调用点
     rg -n "<被删符号>" src/
     ```
     **典型遗漏**：前端类型定义文件（删后端字段必同步）、读源码的守卫测试、
     测试 fixture、被删函数的调用点（清理流程里常藏着对被删符号的调用）。
   - 附加禁令：**禁止全局写命令**——`cargo fmt --all`、workspace 级格式化、
     `git add -A`（实测会污染并行 worker 的文件）；格式化只允许 `cargo fmt -p <pkg>`
     或 `rustfmt <file>`。
   - git 纪律：禁止 `add`/`commit`/`push`/`stash`；**唯一例外** = 撤销自己误改的白名单外
     文件（`git checkout -- <file>`），且必须自报。
4. **强制返回格式**：① 结果状态 ② 改动说明（实测行号+变量名）③ 关键日志（含用例数）
   ④ 遗留债务（含白名单外触碰自报）⑤ 存疑项。
5. **通用纪律**：先读后改；不得弱化/删除任何断言；中文 docstring；探针脚本从 `%TEMP%`
   起或放 `scripts/tmp-*` 且**收工即删**。
6. **变异验证要求（仅当任务含守卫/测试改动时）**：明确告知 worker
   「必须确保变异真的改变了被测行为」——加后缀（`x` → `x-Y`）或删冗余判定
   都不算真变异，会得出「守卫失效/测试有效」的**错误结论**。详见「变异验证」节。

## 协作流程

1. **拆解** → 白名单互斥并行派发（先只读盘点/审查，按结论派修复）。
2. **Worker 返回 → 协调者抽验**：重跑关键命令、核对计数/行号与声明一致。
   - **时效性铁律**：任何「失败/阻塞/红」先用**新鲜状态复核**——陈旧二进制制造过
     假恒红、他人自愈制造过假阻塞（均为实测）；复跑仍红才进入修复派发。
   - **并发假红专项**（单轮出现 3 次）：编译/fmt 报错先看**报错文件是否在你的改动集里**。
     不在 → 极可能是他人并发写入的瞬时快照，**隔 1-2 分钟复跑**再下结论。
     ```bash
     # 判定归属：mtime 时间窗
     ls -la --time-style=+%H:%M <报错文件> <你的改动文件>
     ```
     典型：`error[E0425]: cannot find function X`（函数定义就在下一行）、
     `non-exhaustive patterns`（他人新加枚举变体）、`fmt` 报未跟踪文件。
3. **全绿** → 汇总交付；**红** → 按日志定位 → 派修复 → 再验证。
4. 同一问题**连续 3 次未过** → 停止重试，汇总三次根因 + 已勘挖事实 + 请求用户决策。

## 变异验证（守卫/测试有效性的唯一手段）

目的：证明「守卫真的在拦」或「测试真的在测」——防止改成**静默空转**。

### 硬规则：变异必须真的改变被测行为

以下三种是**无效变异**（测试仍绿，会误导你得出错误结论）：

| 无效变异 | 为什么无效 | 实例 |
|---|---|---|
| 加后缀 `x` → `x-Y` | 子串 `x` 仍存在，守卫的正则/`includes` 本来就该匹配 | `data-metrics-column` → `data-metrics-column-X` |
| 删冗余判定 | 下游函数内部已有同样的过滤，行为不可区分 | 删 `is_timed_chunk`，但 `estimate_block_size` 内部也过滤 `[DONE]` |
| 改注释/格式 | 不触及断言的匹配目标 | — |

**正确做法**：**彻底移除**匹配目标（改成一个不含该子串的全新标识符），
并先确认「该目标是被测断言的唯一来源」。

### 变异验证失败时的处置

变异后**测试仍绿**，只有两种可能，必须先查清再下结论：

1. **守卫/测试是空转** → 真缺陷，立即修（并记入遗留债务）
2. **你的变异无效**（目标不唯一/被下游冗余覆盖）→ 换一个真变异重做

**实测教训**：第一次遇到「仍绿」时曾误判「守卫失效」，实际是变异设计错误。
因此：**「变异后仍绿」≠「守卫失效」**，必须先排除无效变异。

### 无法构造有效变异时

若某段逻辑确实不可测（如纯性能优化、被下游冗余覆盖），**不要假装测到**：
- 在 docstring 写明「此处不可测 + 原因」
- 测试集中到**可区分**的面（如「累计与 metrics 是否一致」「饱和是否生效」）
- 在汇报里如实声明验证边界

## Worker 失败与异常

- **超时/失败**：先盘点其白名单文件的 `git status`，判定「零写入 / 半成品」，三选一：
  ① 回滚 ② 保留半成品、派新 Worker 按「已就位+补齐」收尾 ③ 带已勘挖事实重派。
  **未盘点前禁止叠加新改动**。产出近乎完整时优先走 §6 收尾而非重派（重派要重读上下文）。

  **判定“零写入 vs 半成品”的具体命令**：
  ```bash
  # ① 白名单文件是否被改
  git status --short <白名单文件...>
  # ② 行数/文件是否存在（新建文件的目标）
  wc -l <原文件> <目标新文件> 2>/dev/null
  # ③ 是否可编译（半成品常编译不过）
  cargo check --lib 2>&1 | grep -c '^error'
  ```
  **零写入**：`git status` 空 + 行数未变 + 无新文件 → 直接重派，无需回滚。
  **半成品但可编译 + 测试绿**：走 §6 收尾。
  **半成品且编译不过**：先看报错是否集中在一个未完成的改动上；是则派新 worker 收尾。

- **前提错误**：Worker 用证据推翻任务书前提 → 协调者独立复核后采纳、修正方向
  （高价值输出，不是抗命）。**实例**：worker 实测发现「三处是未提交 WIP」
  实为已合入的历史提交；scout 实测发现「HTTP 客户端不读系统代理注册表」是错的
  （其 feature 默认开启）。两者都直接改变了修复方向。

- **范围冲突**：先核实事实再裁决（批准/否决 + 理由）；豁免最小化并记录在案。
  **裁决必须含**：① 批准哪些文件 ② 每文件的**具体改动范围**（不能只说「允许改」）
  ③ 硬约束（如「字段保留不删」「夹具不删只补」）④ 修订后的验收口径。

- **双写撞车预防**：两个 worker 可能同时需要改同一文件（如共享类型定义文件）。
  裁决时必须**明确指派唯一负责方**，并向另一方发 steer 收回该文件：
  > 「`<文件>` 不由你改 —— 另一个 worker 负责。你的白名单移除它。」
  否则会出现互相覆盖或 git 冲突。

- **测试变更请求**：区分「测试替身不完整（补 mock，允许）」与「弱化断言（禁止）」。
- **存疑销账**：Worker 的 ④⑤ **逐条处理**——采纳进遗留债务或驳回给理由；
  **禁止静默丢弃**。

## §6 协调者亲自收尾（默认禁写代码的唯一例外）

同时满足：

1. 已 **3 次派发失败**，或属**验收级小修**（≤20 行；含超时留尾：fmt/clippy 单点、计数修正）；
2. 契约/方案已由 Worker 或自证勘挖明确；
3. 用户知情或已明确授权同类操作；
4. 完成后照常走完整验证与汇报。

## 汇报纪律

- 每次派发或收到结果：**进度表**（Worker / 范围 / 状态）+ 下一步计划。
- 最终交付：任务状态、改动摘要（按 commit 分批）、**可否证命令**（如
  `git ls-remote origin main` 与本地 HEAD 比对）、遗留债务清单（附建议处理方式）。
- **提交范围硬核对**：commit 后必查 `git show --stat`；混入白名单外文件时评估危害
  并显式说明，不得沉默带过。
- **工作区卫生**：每轮清点探针脚本 / 临时文件 / 未跟踪文件归属；他人 WIP **显式隔离**
  （不提交、不修改）并向用户说明。
- **WIP 归属判定法**：mtime 时间窗 × 各 worker 活动窗 × transcript grep × 提交历史，
  四方交叉；判不出就不碰、汇报待裁。

## 经验法则（历史会话实测）

- 驳回「凭快照硬改」：先实测再动手，漂移即重新定位。
- 「零引用/死代码」结论必须附**检索命令+范围+排除项**；宣称完成必须附**原始验证输出**。
- Worker 报告与事实冲突（计数/行号/前提）→ 以**协调者复核实测为准**，回写台账。
- 并行数量：只读 4+、写入 2-3；瓶颈通常出现在协调者验收环节。
- **白名单不全是最贵的返工源**：派发前必跑四类检索（守卫/类型/夹具/连带死代码）。
  漏一个 = 一次 worker 停下来请示 + 一轮协调者裁决 + 可能一次双写冲突。
- **「变异后仍绿」先怀疑自己的变异**，再怀疑守卫。加后缀、删冗余判定都不算变异。
- **「编译失败」先看报错文件是否在你的改动集里**：不在 → 大概率是他人并发写入的瞬时快照，
  隔 1-2 分钟复跑。**别急着改别人的代码，也别急着回滚自己的**。
- **保守就胜**：把「无法验证」当作「不安全」处理（fail-closed），
  把「无法确认」当作「未完成」汇报——**不要用猜测填补证据缺口**。
  实例：出站白名单检查曾读配置态而非运行态 = fail-open，已修为快照缺失即拒绝。
- **禁止用“加个开关”修语义污染**：拆键必须拆到「一个键只说一件事」。
  实例：`proxy_enabled` 同时承担「跟随系统代理」与「全渠道出站开关」
  → 用户关闭无效 → 拆为 `proxy_follow` + `upstream_proxy_url`。
- **旧键迁移必须继承旧语义的启用条件**：无条件搬值会让「用户已关闭的东西复活」。
  实例：迁移代理地址时未看旧开关状态，导致已关闭的代理升级后重新生效。
- **前后端契约改动必须同时改 4 处**：后端结构体 / 前端类型定义 / 测试夹具 / 只读兼容层。
  只改前两处 → 类型检查或运行时 `undefined.trim()` 白屏。
